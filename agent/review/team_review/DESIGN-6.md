# 6. 평가 기준 설계 - 팀 검토용 구현안

판교 7반 2조 / 백순철 / RDKV(SW-01)·Photonic-CXL(HW-01)

아래 기준은 `team_review/rubric.py`와 `review.py`에 대응한다.
이 문서는 평가 기준이며 두 기술의 실제 성능이나 TRL을 판정한 보고서가 아니다.

## 6.1 관점별 평가 기준

| 관점 | 평가 대상 | 판단 기준 | 필요 근거 |
|---|---|---|---|
| 기술 성숙도·기술 조사 | 원리·검증 범위·TRL | 해당 구현의 검증 환경과 통합 범위를 6.2에 대응한다. 확인한 최고 연속 단계와 상위 단계의 증거 공백을 분리한다. | RDKV v1의 구현·GPU 실험, Photonic-CXL v1의 하드웨어 에뮬레이션·서빙 시뮬레이션. 장비·워크로드·기준선·원문 위치. |
| 시장성 | 규모·성장·상용화·채택·생태계·비용·고객 가치 | 두 기술에 같은 항목을 적용한다. 사업화 방식은 가설로 두고 공식 제품·도입·지원·비용 자료로 검증한다. 넓은 AI 시장을 해당 기술 시장으로 대체하지 않는다. | 자료의 지역·기간·단위, 제품 출시·도입 사례, 공식 프레임워크 지원·표준 자료. 미확인 수치를 생성하지 않는다. |
| 이해관계자 | 경쟁사·도입자·개발자·투자/애널리스트/미디어 | 직접 입장과 평가자의 이해관계 추론을 구분한다. 편익·비용·경쟁 관계 및 제약을 함께 기록한다. | 당사자 원문·실제 적용 경험·투자 및 분석 자료의 발행 주체·시점·입장·근거 위치. |
| 도메인 적용 | 장문맥 문서 QA를 제공하는 데이터센터·클라우드 | 공통 10기준을 목표 요구와 연결한다. 요구값이 없으면 충족을 단정하지 않고 조건부 평가 또는 미확인으로 남긴다. 온디바이스는 보조 시나리오다. | 모델·문맥 길이·동시성·메모리·TTFT·토큰 지연·처리량·품질 허용치·비용. 실험과 목표 환경의 차이. |

공통 10기준의 ID는 `capacity`, `quality`, `latency`, `throughput`, `gpu_compatibility`,
`hardware_dependency`, `deployment`, `maturity`, `customer_value`, `domain_fit`이다.

**입력과 판단 원칙**

- `favorable`: 선택 도메인의 명시된 요구조건 충족 근거가 있다. 기술 전체의 우수 판정이 아니다. 기존 `met` 입력은 호환 목적으로 받되 MD에는 favorable로 출력한다.
- `unfavorable`: 선택 도메인의 핵심 요구조건과 충돌하는 근거가 있다.
- `not_applicable`: 기술/도메인에 적용되지 않으며 평가 문장에 이유를 명시한다.
- `conditional`: 근거가 있으나 적용 조건·제약이 붙는다. 반대 근거도 결론과 한계에 보존한다.
- `unknown`: 판단할 근거가 없다. 성능이 나쁘거나 시장에서 반대한다는 의미로 바꾸지 않는다.
- `basis=fact`: 원문이 직접 보고한 내용. 저자의 주장을 독립 검증된 사실로 바꾸지 않는다.
- `basis=inference`: 근거에서 도출한 평가자의 해석. 전제가 되는 출처를 함께 연결한다.
- `failed`: 분석 또는 도구가 실패했다. 자료가 없는 unknown과 구분한다.
- `need_more`: 실제로 보완 검색할 질문. 조사했지만 확인되지 않은 항목은 gaps에 남기고 불필요하게 반복하지 않는다.

각 역할은 `criterion_id`, `judgment`, `conclusion`, `conditions`, `evidence_ids`, `basis`, `gaps`,
`need_more`를 반환한다. 성능 수치가 있으면 `metrics`에 지표·단위·실험 조건을 별도 기록한다.
최종 계약 `kv-cache-rubric-v1`에 따라 `analysis_scope`, `domain_relevance`, `confidence`, `counter_evidence`도 전달한다.
원문 입력과 정규화 도메인을 구분하고, 목표값을 모르면 TBD로 둔다.

## 6.2 TRL 단계별 판정 기준

NASA의 SW/HW별 TRL 설명을 참고해 이번 과제에 맞게 정리한 팀 적용안이다.
공식 인증 또는 NASA에 의한 해당 기술의 판정이 아니다.

| TRL | 판정 기준 | 필요 증거 |
|---|---|---|
| 1 | 기본 원리 관찰·보고 | 기술을 뒷받침하는 이론·원리의 문서화된 근거 |
| 2 | 기술 개념·적용 방식 정립 | 해당 알고리즘/구조와 적용 목적·예상 편익 |
| 3 | 핵심 기능의 개념 검증 | 핵심 가설을 확인한 분석·실험·모델링 결과와 조건 |
| 4 | 실험실에서 핵심 구성요소 통합·검증 | 구현된 핵심 요소, 통합 범위, 시험 결과, 목표 환경 정의 |
| 5 | 목표와 관련된 환경에서 검증 | 대표 워크로드·연동 환경·요구 성능·확장 조건의 검증 |
| 6 | 대표 규모에서 시스템 시제품 시연 | 통합 시제품의 시스템 수준 시험과 주요 확장 문제 검증 |
| 7 | 실제 운용 환경에서 시제품 시연 | 운용 HW/SW와 연동한 파일럿 또는 현장 시연 기록 |
| 8 | 완성 시스템의 적합성 검증 | 최종 구성의 기능·성능·안정성 검증과 운영·유지보수 문서 |
| 9 | 실제 환경의 성공적 운용 | 실제 운용 결과와 지속적인 운영·유지보수 근거 |

출처: [NASA ESTO TRL 기준](https://esto.nasa.gov/trl/).

**판정 절차**

1. technical 담당은 각 기술의 `trl_checks[1..9]`에 `met/not_met/unknown`, 근거 ID, 판정 이유를 넣는다.
2. review는 출처의 존재·대상 기술·v1·페이지와 체크리스트의 연속성을 확인한다.
3. 1단계부터 필수 조건이 연속으로 확인되는 최고 단계를 반환한다. 낮은 단계의 조건도 근거로 명시해야 한다.
4. 어떤 단계도 확인할 수 없으면 `level=null`. 상용화 근거가 없더라도 확인된 하위 단계까지 모두 null로 지우지 않는다.
5. 실제 운용 단계는 에뮬레이션·시뮬레이션만으로 통과시키지 않는다. 7·9는 운용 근거, 8은 완성 시스템 검증/운용 근거가 필요하다.
6. GPU 실험 유무·논문 공개·유명 기업 여부만으로 단계 숫자를 자동 부여하지 않는다.
7. 검수자는 체크리스트의 met가 실제로 해당 단계 조건을 충족하는지 원문으로 확인한다. 코드의 형식 검사만으로 이를 보증하지 않는다.

| 항목 | 설계 내용 |
|---|---|
| 대상 및 기준 시점 | RDKV 구현과 Photonic-CXL 어플라이언스 구조의 v1 검증 범위. 일반 양자화·CXL 표준의 성숙도를 대입하지 않는다. |
| 이후 공개 자료 | 최신 배포·운용 자료는 시장/도메인 평가에서 조사 시점과 함께 별도로 다룬다. v1 TRL에 섞지 않는다. 최신 TRL을 별도로 평가하려면 팀이 기준 시점을 변경해야 한다. |
| 공개 정보 공백 | 상용화·가격·운용·독립 재현 자료가 없으면 해당 항목만 미확인으로 남긴다. 실제로 존재하지 않는다고 결론 내리지 않는다. |
| 공개 정보 기반 추정 | 모든 TRL 출력에 공개 정보 기반의 팀 추정이며 실제 내부 개발·배포 수준을 확정하지 않는다는 문구를 붙인다. |
| 사실·추론 및 편향 | 원문 보고, 팀 해석, 최신 외부 조사 결과를 구분한다. KV 원본 보존이 서비스 정확성이나 법률·의료 분야의 우위를 보장한다고 해석하지 않는다. |
| 실험 조건 차이 | decode 가속과 TTFT 개선은 다른 지표다. 모델·장비·기준선·워크로드·평가 방식이 다른 배수를 직접 나누거나 순위화하지 않는다. |

## 검증·종합(review)의 처리 규칙

| 검사 | 처리 |
|---|---|
| 두 기술 × 네 관점 | 8칸을 항상 출력하되 누락 칸을 unknown/failed로 드러낸다. 출력 8칸과 유효 입력 8칸을 구분한다. |
| 인용 | 존재·원문 확보·페이지 범위·기술 연결을 검사한다. 잘못된 인용이 붙은 확정 결론은 판단 보류로 바꾼다. |
| 관점별 차이 | 같은 기술/criterion_id의 판정 차이를 모은다. 조건 차이를 실제 모순이라고 자동 단정하지 않는다. |
| 조건부 종합 | 검증된 결론·조건·근거를 나란히 배치한다. 새 시장·성능 주장은 생성하지 않는다. |
| 추가 평가 | 보완 가능하고 round=0이면 dirty 역할만 1회 재평가한다. technical 보완 시 후속 역할도 재평가 대상으로 표시한다. |
| 종료 | 모든 필수 검사가 충족되면 completed. 자료 공백·일부 실패·TRL 보류는 partial. 입력/치명적 실패·전체 실패는 failed. round=1이면 재평가를 더 요청하지 않는다. |
| 참고문헌 | 최종 출력에 실제 사용한 근거 ID의 문서와 원문 위치만 전달한다. |

새 종합 의견과 연결된 평가·발췌의 의미적 연결은 자동 검사한다. 고위험 단정은 규칙으로 반려하고,
나머지는 별도 모델 호출로 대조한다. 필요 시 한 번 수정하고 재검사하며, 미통과 결과는 후단 전달을 차단한다.
입력 자료 자체의 진실성·비용 추정 현실성까지 보증하지 않으며, 실행 중 사람의 승인 단계는 없다.

## 교재·필기에서 반영한 범위

- State: 기존 결과·근거·회차를 공유하고, review/synthesis 키만 부분 갱신한다.
- Modular 구성: 검색·분석·검증·출력을 역할에 맞게 분리한다.
- Branch/Loop: 세 분석 분기의 완료를 기다리고, 보완이 필요한 역할만 1회 반복한다.
- Query rewriting: 추가 검색은 상위 담당에게 전달한다. 종합부는 생성·의미 검사 정상 2회, 수정 포함 최대 4회로 제한한다. 자료 공백을 새 사실로 채우지 않는다.
- 검증 범위: 규칙 검사, 입력과의 의미 정합성 검사, 외부 사실의 진실성을 구분한다.

현재 모듈은 규칙 기반 검증과 제한된 생성·의미 검사 루프다. Self-RAG 논문의 Reflection Token이나 자율 도구 선택을 구현했다고 주장하지 않는다.
필기의 "CXL은 GPU를 반드시 재설계해야 한다", "특정 기업은 사용할 수 없다" 같은 문장은 평가 규칙에 넣지 않았다.
구체적 호스트 경로·인터페이스·배포 사례를 원문에서 확인한 경우에만 분석 결과로 반영한다.
