# 시장조사 에이전트 설계 v0.4

- 갱신일: 2026-09-22. 기술 조사 JSON 입력을 받아 시장 담당 항목과 인용이 들어간 MD 한 개를 반환한다.
- 대상: RDKV(SW-01), Photonic-CXL(HW-01), cloud_datacenter. 현재 실제 검증 기준일은 2026-09-22.
- 관련 문서: [실행 안내](../market_agent/README.md), [구현·검증 계획](../tasks/plan.md), [작업 기록](../tasks/todo.md).

## 1. 목적과 역할 경계

기술 조사 결과를 출발점으로 공개 자료에서 시장성의 근거를 조사한다. 기술 성능, 기술 성숙도, 기업의 이해관계, 목표 서비스의 적합성을 시장 전체의 결론으로 대체하지 않는다.

| 역할 | 책임 |
| --- | --- |
| technical | 기술 원리·성능·실험 조건·한계·TRL 근거 |
| market | 시장 규모·성장, 제품화, 채택, 공식 지원, 표준, 고객 가치·사업화 조건 |
| stakeholders / domain | 이해관계자 입장 / 목표 환경의 요구 충족 여부 |
| review / render | 관점별 결과 검토·종합 / 전체 보고서 생성 |

시장 출력은 입력 기술마다 6개 항목과 실제 인용으로 한정한다. 무조건적인 우승 기술, 가상의 고객·가격·ROI를 만들지 않는다. 미확인도 명시적인 결과다.

## 2. 입력 계약

현재 기본 입력은 dossier 1.0.0 두 개 + 공통 evidence_registry 배열 + comparison 1.0.0으로 구성된 JSON 네 개다. 참조 ID·문서 소유 관계·본문/문서 해시와 비교 배열 형식을 API 호출 전에 검사한다. 비교 불가능 조건과 미검증 결합 가설은 모델의 배경으로 보존한다.

호환 입력으로 기술 조사 paper_analysis JSON schema_version 1.1.0 / status succeeded를 받는다. 단일 논문 객체, 최대 두 파일, 두 객체의 배열을 지원한다. `paper`, `analysis`, `evidence_registry`를 검증해 기존 MarketInput으로 정규화하며, 원래 `quality`, `run`, `diagnostics` 등도 내부에 보존한다. 기존 Markdown v0.1 파서는 호환 유지한다.

RDKV/Photonic-CXL은 제목으로 분류하고 다른 논문은 호출자가 `--approach`로 지정한다. 임의 로컬 source_path를 읽거나 파일명으로 공개 URL을 추정하지 않는다. JSON의 미제공 기준일은 실행일, 도메인은 cloud_datacenter, 전체 호출 한도는 6/10/5다. 실행 옵션으로 재정의할 수 있으며 상위 run의 모델·예산을 상속하지 않는다.

원래 paper_id·evidence_id·페이지·절·claim_type·confidence·인용 관계를 보존한다. 전달된 논문 발췌는 provided_summary로 취급하며 웹으로 독립 확인한 시장 사실과 구분한다. 추출 모델에는 기술 배경을 논문당 최대 6,000자 제공한다. 자세한 계약은 [JSON 입력 안내](JSON_INPUT.md)에 있다.

## 3. 수집과 본문 품질

검색은 기술 자체의 구현·라이선스와 관련 기술군의 시장·지원·비용으로 범위를 나눈다. LLM이 제안한 질문은 우선순위로 활용하며, 실제 질의는 기술명·기술군·항목별 키워드로 구성한다. RDKV 동명 TV 플랫폼 자료는 KV cache 문맥 검사로 제외한다. 공식 도메인은 후보 순위의 단서이며 모든 주장의 진실성을 보장하지 않는다.

추출 요청 성공과 내용 확보를 구분한다. Evidence의 access_status는 provided_summary/full_text/snippet/failed, content_status는 unchecked/substantive/metadata_only/identity_mismatch다. 내용 검사에 실패한 full_text 자료는 추출 모델에 전달하지 않는다.

내용 검사는 제목·메타데이터·메뉴 이외의 문장, 논문 제목의 대상 일치 등을 확인하는 휴리스틱이다. 짧은 제품 발표를 길이만으로 버리지 않는다. 내용이 없으면 같은 버전의 논문 공개 경로를 최대 한 번 더 조회한다. 이미지·표·PDF의 완전한 판독이나 의미상 신뢰도를 보장하는 검사는 아니다.

## 4. 원문 구절과 주장 계약

첫 실제 재검증에서 LLM이 원문 인용을 다시 쓰고 요약을 사실로 사용하는 문제가 남아 있어, 추출 단계도 **원문 구절 ID 선택**으로 제한했다.

1. 품질을 통과한 자료의 관련 문단을 위치와 함께 선택한다(자료당 최대 12,000자).
2. quotes.py가 시장 관련 완전한 문장을 원문에서 선택해 고유 ID를 발급한다. 문장당 최대 100단어, 자료당 최대 10개다. 25단어씩 자르는 방식은 주장 범위가 어긋나 폐기했다. 링크 조각·일부 수식 깨짐을 제외하며 최종 외부 발췌만 URL당 25단어로 제한한다. 이 선택 범위 밖의 정보를 전부 검토한 것으로 표현하지 않는다.
3. LLM은 실제 원문의 기술별 quote_id enum과 대상 명칭 후보에서 선택한다. 해당 기술 이름이 후보 원문에 없으면 exact 선택을 제한한다. 평가 항목, 한국어 주장, 사실/추론, 관계, 조건, 선택적 metric을 작성한다. 자유로운 URL·인용문·근거 ID를 작성하는 필드는 없다.
4. 코드는 quote_id를 원문의 문자열·출처·위치로 변환한다. 없는 ID는 다른 문서로 임의 연결하지 않고 오류로 처리한다.
5. claims.py가 인용·시점·대상·범위·조건·수치를 검사하고 Claim ID를 부여한다. 같은 자료의 같은 인용·항목은 중복 등록하지 않는다.

웹 근거 추출 모델에는 전달받은 논문 요약을 인용 후보로 넣지 않는다. 내부 검증기는 이전 부모 상태를 읽을 때 요약 기반 고객 가치의 조건부 추론만 제한적으로 허용한다. 요약과 웹 인용을 섞어 상용화 사실로 바꾸지 않는다.

발행자의 보고라는 귀속을 문장에 표시하고 could/may/might/potential은 inference와 가능성 조건으로 처리한다. 문자열 일치는 의미상 입증과 다르다. 모델이 원문보다 강한 한국어 주장을 작성할 수 있으므로 라이브 결과의 주요 주장은 사람이 원문과 대조한다. 제품 사양·연구 성능을 시장 규모나 ROI로 바꾸지 않는다.

## 5. 평가와 관련 정보 보존

평가 모델은 원문 전체 대신 문자열·대상 검사를 통과한 Claim 목록을 받는다. 모든 Claim에 supported, market_relevant, relation_supported, conditions_preserved, evidence_level과 reason을 반환한다. 코드도 제품화·채택·지원·고객 가치 항목의 최소 근거 요건을 검사한다. 최종 전달 후보는 별도 모델 호출에서 다시 검토하며 기각된 주장을 제거한다. 검토 누락은 처리 오류, 명시적 거부는 제외 사유로 기록한다. 검토를 통과한 Claim만 평가·관련 정보에 연결한다. DraftAssessment는 claim_ids로 참조하고 코드는 이를 Citation으로 변환한다. 제품화·실제 채택은 직접 근거가 없으면 unknown으로 둔다. 나머지 네 항목은 의미 검토를 통과한 관련 근거와 적용 조건으로 조건부 추론할 수 있다. 확인된 문장은 선택한 Claim의 문장을 그대로 연결하여 모델의 추가 성과 주장을 방지한다. 제품화·실제 채택은 exact만, 시장 규모·생태계·표준·고객 가치는 같은 기술·항목의 method_family/adjacent도 허용한다. 관련 근거를 선택하면 inference/conditional 및 범위 설명을 강제하며 사실로 승격하지 않는다.

| 구분 | 의미 |
| --- | --- |
| verdict | favorable/conditional/unfavorable/unknown/not_applicable. 도입 판단 |
| basis | fact/inference/unknown. 근거 성격 |
| relation | exact/method_family/adjacent/unknown. 선정 기술과의 관계 |
| context_findings | 검증된 관련 기술군·제품 정보와 한계 |

조직의 구매 목표가 없으므로 무조건적 favorable/unfavorable을 확정하지 않는다. 관련 제품의 출시·지원은 선정 논문 구현의 상용화와 동일하지 않다. 직접 판정이 unknown이어도 검증된 관련 정보는 코드가 항목당 최대 1건 연결한다. 추가 근거는 포함/제외 이유를 내부에 남긴다.

잘못된 인용은 해당 Claim 단위로 제외한다. 독립된 유효 Claim은 유지한다. 평가가 잘못 연결한 Claim을 삭제한 채 그 결론을 유지하지 않고 미확인과 처리 사유를 반환하거나 해당 평가를 다시 작성한다.

## 6. LangGraph와 보완

`collect → extract(근거 선택·검증) → compose(평가·인용 검사) → audit(최종 후보 재검토) → finish`

수집·추출·평가 보완은 각각 최대 1회다. 같은 전체 예산 안에서 필요한 단계만 선택한다.

| 상태 | 보완 경로 |
| --- | --- |
| 근거 부족·미조사 항목 | collect → extract → compose |
| 구절·대상 연결 오류 | 보유 원문으로 extract → compose |
| 평가의 Claim 참조 오류 | compose만 재실행 |
| 인증 실패·사용량 부족·보완 소진 | 확인한 정보와 구체적 미완료 사유로 종료 |

관련 근거가 존재하면 실제 제공자에서는 평가 작성·최종 검토 각 1시도를 먼저 확보하고 추가 추출을 결정한다. 이미 검토한 원문이고 새 자료도 없으면 중복 추출을 생략한다. 충분한 원문이 없으면 LLM 호출을 생략하며, 근거 풀이 비어 있으면 평가 작성도 생략한다.

| 자원 | 상한·제어 |
| --- | --- |
| 검색 | 입력 상한 6, 초기 최대 2질의 / 보완 최대 4질의, 전송 재시도 포함 |
| 원문 | 입력 상한 10, 최초 최대 6시도, 대체 URL·실패도 차감 |
| LLM | 입력 상한 5, 추출·작성·최종 검토 및 한도 안에서 단계별 보완, 전송 재시도 포함 |
| 시간 | Tavily 시도당 20초, OpenAI 시도당 60초 |

두 단계가 각각 SDK에서 자동 재시도하지 않도록 설정하고 Budget에서 관리한다. 더 작은 부모 할당량을 받으면 축소하며 회차가 바뀌어도 사용량은 초기화하지 않는다.

## 7. 저장과 부모 연결

외부 입력은 JSON을 기본으로 확장했으며 시장성 표 계약은 기술당 6개 항목이다. 내부 스냅샷/MarketResult 버전은 0.4이며, 프롬프트·코드 fingerprint로 구형 캐시 재사용을 막는다.

- 전달: market_handoff.md 한 개.
- 내부: 전체 추출 응답, Evidence, candidate_pool, 의미 검토 통과 claim_pool, claim_review_log, source_reviews, claim_dispositions, 오류·사용량·파일 해시.
- 선택 진단: --debug의 추출/평가 모델 응답과 Graph 경로.
- 제외: 키·내부 캐시·원문은 Git과 통합용 전달에서 제외한다.

부모는 run_market(auto_repair=False), 같은 역할별 Budget, round_number 0/1, previous, existing_evidence, existing_claims와 previous_progress를 전달한다. progress에 조사·오류·검토 이력을 보존하여 새 호출 없이 partial이 completed로 바뀌지 않는다. parent_update는 assessments.market와 새 documents/evidence/errors만 반환한다. 다른 역할 결과를 덮어쓰지 않도록 ID 기반으로 병합한다. 부모 checkpoint와 총 페이지 집계는 별도 통합 범위다.

## 8. 검증 기준

- 메타데이터뿐인 원문·다른 논문 인용·요약 혼합·임의 구절 ID를 차단한다.
- 유효한 관련 제품 정보는 선정 기술이 미확인이어도 표와 인용에 남는다.
- 실패/한도/부모 회차/캐시 무결성을 검사하고 API 실행 성공과 조사 품질을 분리한다.
- 기존 사례 및 새 회귀 검사 이후 실제 입력으로 실행하고 원문과 최종 문장을 대조한다.
- 미확인 감소 개수를 성공 기준으로 삼지 않는다. 작은 조사 범위 밖의 시장 부재를 주장하지 않는다.

실제 실행별 결과와 남은 한계는 [LIVE_VALIDATION.md](../market_agent/LIVE_VALIDATION.md)에 기록한다. 실습 가이드의 이전 검토 기록은 [KV_CACHE_GUIDE_AUDIT.md](KV_CACHE_GUIDE_AUDIT.md)에 보존되어 있다.

## 9. 실제 검증에서 추가한 보호 장치

- 처음의 자유 인용 생성은 원문 구절 ID 선택으로 바꾸었다.
- 잘린 구절과 의미를 넘는 설명은 완전한 문장 선택과 작성 단계의 의미 검토로 보완했다. 검토 모델도 오판할 수 있으므로 주요 최종 문장은 원문 대조가 필요하다.
- 평가 작성 기회가 없으면 새 후보를 최종 근거로 자동 승격하지 않는다. 재작성 시에는 탈락 전 후보를 보존하여 검토 누락이 조용히 사라지지 않게 한다.
- 직접 근거 없는 항목은 모델의 잘못된 fact/conditional 출력 대신 코드가 unknown으로 고정한다. 관련 제품 발표는 별도 관련 정보에 남긴다.
- 모델이 선택한 주장 수나 unknown 감소가 품질의 합격 조건은 아니다. 실측 비용·실제 고객·시장 규모를 확보했는지 별도로 읽어야 한다.


## 10. v1.2 실행 상태와 검증 한계

`execution_status`는 completed/partial/failed이고 시장 판정 status·verdict와 별개다. 정상 조사 후에도 직접 근거가 없으면 unknown이다. CLI 종료 코드는 0/3/2다. 부분 결과와 구버전 캐시는 성공 재사용하지 않는다. 전달용 MD의 항목별 조건·공백에는 결론 해석에 필요한 한계만 남긴다.

기술 성능이나 공급사 전망은 고객 비용·매출의 실측과 다르다. 관련 제품 정보는 선정 논문에 대한 제품화 근거로 승격하지 않는다. 문자열 필터와 모델 검토는 완벽한 의미 검증이 아니므로 실제 실행마다 최종 인용을 원문과 대조한다. 최신 실행 기록은 LIVE_VALIDATION.md에 있으며 위 v1.1 기록은 당시 결과다.


## 11. v1.3 항목별 근거 정책

| 항목 | 허용 근거 | 판정의 의미 |
| --- | --- | --- |
| 제품화·실제 채택 | 선정 기술과 연결된 직접 근거 | 관련 제품 출시·사용은 보조 정보로만 제공 |
| 시장 규모·성장 | 직접 근거 또는 관련 시장 자료 | 관련 시장 활동을 조건부 해석; 선정 기술의 매출·점유율·TAM 아님 |
| 생태계 지원 | 직접 지원 또는 관련 기능·통합 자료 | 통합 가능한 경로의 조건부 평가; 선정 구현 지원 인증 아님 |
| 표준화 | 직접 근거 또는 활용 가능한 관련 규격 | 적용 규격의 조건부 평가; 선정 구현의 규격 준수 인증 아님 |
| 비용·고객 가치 | 기술적 전제·공급사 자료·고객 실측 | 자원 효과와 운영 조건에 따른 추론; 실측 ROI와 구분 |

- 정책은 `policy.py`에서 정의하고 모델의 선택지, `materialize`, 최종 검증 및 재개 경로에 적용한다.
- 관련 근거는 모델이 명시적으로 선택하고 조건을 작성해야 한다. 근거가 있다는 이유만으로 unknown을 자동 변경하지 않는다.
- `provided_summary`의 등록 발췌를 기술당 최대 2개 선택하고 각 발췌에서 최대 4개 구절을 제공한다. business_value/inference/exact/metric=null 범위만 모델 스키마에서 허용한다. exact는 입력 논문의 소유 관계를 뜻하며 독립 웹 검증이나 실제 고객 성과를 뜻하지 않는다.
- 인용은 원문 구절과 연결하고, 등록 소유 관계 및 원래 실험·에뮬레이션·시뮬레이션 조건을 보존한다. 비교 불가능한 성능 수치를 합산하거나 ROI로 환산하지 않는다.
- 숫자는 Decimal로 천·백만·십억·조 배율을 정규화한다. 통화/수량/백분율, 연도, 지역, 대상, 실제/전망을 함께 검증한다. 생산량과 생산능력은 같은 문장의 다른 절에서도 구분한다. 이 검사는 인용 의미의 모델 검토를 대체하지 않는다.
- 마지막 LLM 호출을 사용했어도 정상 검토한 unknown에는 예산 부족 원인을 붙이지 않는다. 실제 한도 오류 또는 조사하지 못한 항목의 한도 부족만 기록한다.
- 외부 출력은 여전히 기술당 6개 항목과 인용 근거가 있는 MD 한 개다. 내부 필드 계약 0.4는 유지하며 프롬프트 v8와 코드 fingerprint로 이전 정책의 캐시 자동 재사용을 차단한다.


### 항목별 추출 응답과 API 제약

최초 개선 실행에서는 자유 목록 추출의 12개 슬롯을 기술 성능 설명이 차지했다. 모델 응답을 `claims[기술ID::항목]` 배열로 나누고 각 항목에 최대 2개만 허용한다. 코드가 슬롯의 기술·항목을 내부 Claim에 주입하므로 모델이 다른 항목으로 이동시키지 못한다. 근거가 없으면 빈 배열이다. 자료별 reviews도 ID를 키로 하는 필수 객체로 받아 검토 누락을 줄인다. 내부 Extraction/Claim 계약은 변환 어댑터로 유지한다.

구조화 출력은 공통 대상 명칭과 재사용 가능한 선택지를 `$defs`/`$ref`로 정의한다. 인용 후보는 항목별 최소 주제 요건을 충족하는 구절로 제한하고 후보가 없는 항목은 빈 배열로 받는다. 직접 복제하면 enum 총수가 API 한도를 넘기므로, 동일 후보의 항목별 중복 정의를 없앴다. [OpenAI Structured Outputs 공식 규격](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas)을 확인했고, 실제 수집 자료에서 중복을 제거한 스키마 enum 수는 439개, 이후 항목별 인용 후보 분리까지 적용한 최종 스키마는 541개로 확인했다. 중복 정의 단계의 2,019개보다 작다. 원문의 연속 문자열 후보와 인용별 연결 검사는 유지한다.

조건부 평가가 관련 사실을 참조하며 적용 조건을 갖추었지만 모델이 basis=fact로 보냈다면 최종 basis를 inference로 낮춘다. unknown을 자동으로 conditional로 변경하지 않으며 최종 문장은 선택한 근거와 범위 안내만 사용한다.
